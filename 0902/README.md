## 1. BFS（廣度優先搜尋）為何能找到無權重圖的最短步數？


BFS 很像把一塊石頭丟進水池後產生的水漣漪。漣漪不是隨機跳到遠方，而是從中心開始，一圈一圈向外擴散。
像是你人在客廳，要在家裡尋找遙控器。

你可能按照距離依序尋找：

1. 先檢查客廳附近的沙發。
2. 接著檢查隔壁的廚房。
3. 最後才前往二樓臥室。

這種搜尋方式不是先挑一條路一路走到底，而是把目前距離最近的位置全部檢查完，再前往下一層。

因此BFS 第一次發現某個位置時，就代表目前沒有使用更多 edge 的繞路比它更早到達。

## 2. `visited` 應在 `offer` 還是 `poll` 時加入？

#

應該在準備將 vertex 放進 Queue，也就是 `offer` 時，就立刻標記 `visited`。

像是正在準備學校舞會邀請名單。

當你決定邀請小明並寄出邀請信時：

```text
寄出邀請信 → offer
標記已邀請 → visited
```

這兩件事情應該一起發生。

如果等到小明真的抵達派對，也就是 `poll` 時才標記，那麼在等待期間，其他朋友可能又推薦小明。

結果就可能變成：

```text
邀請小明
邀請小明
邀請小明
邀請小明
```

同一個人因此被重複放進 Queue。

在 Graph 中，如果存在許多相互連接的 vertex，這種重複 enqueue 不只浪費時間，也會增加 Queue 的空間使用量。

## 3. Recursive DFS 與 Iterative DFS 的 Stack 在哪裡？


兩種 DFS 都具有「先深入、走不下去再回頭」的特性，但保存回頭資訊的位置不同。

```text
Recursive DFS
→ 系統管理的 Call Stack

Iterative DFS
→ 程式自己建立的 Stack
```

前者是隱式（implicit），後者是明確（explicit）的資料結構。


## 4. `start == target` 時，何時應回傳 `[start]`？



起點與終點相同時，可以得到一條包含起點本身、使用 0 條 edge 的路徑，但前提是這個 vertex 仍存在於 Graph。

還需要確認 vertex 是否存在。

如果有人問: 從「台北車站」走到「台北車站」怎麼走？

因為台北車站確實存在，所以根本不需要移動：

```text
路徑 = [台北車站]
edge 數 = 0
```

但如果地圖資料中根本沒有「D地下城」，即使詢問：
從「Z區地下街」走到「D地下城」怎麼走？

也不能只因為兩個名稱相同，就宣稱存在合法路徑。

5. Isolated Vertex 算不算一個 Component？

通常算是，
Isolated vertex 雖然沒有任何 edge，但它仍然是 Graph 中實際存在的 vertex。

C 沒有和任何其他 vertex 相連，但 C 仍然構成：
[C]這個 connected component。


可以把 Graph 想成由許多島嶼組成的地圖，因此可以互相抵達：
```text
島 A ─── 島 B
```

海上另外存在一座完全沒有橋梁的荒島 C：

```text
島 C
```

即使沒有任何交通方式連接 C，它仍然真實存在於這張地圖上，因此計算區域時仍然必須把它計入。

這也說明了 isolated vertex 和 missing vertex 的差異：

```text
Isolated vertex
→ 存在於 Graph，只是沒有 edge

Missing vertex
→ 根本不存在於 Graph
```

## 6. HashMap 平均 O(1)，代表永遠都是 O(1) 嗎？
通常無法這樣認為，HashMap 的 O(1) 通常指平常狀態但極端情況不行，。

HashMap 會利用 hash function 將 key 對應到某個 bucket：

```text
Key
 ↓
Hash Function
 ↓
Bucket
 ↓
Value
```

如果資料分布良好，就能非常快速地找到目標位置。
想像一棟大樓有 100 個信箱。

正常情況下，郵差會依照住戶地址，把不同人的信件放進不同信箱：

```text
A 住戶 → 01 號信箱
B 住戶 → 37 號信箱
C 住戶 → 82 號信箱
```

因此住戶只需要找到自己的信箱，就能快速拿到信件。

但如果大量信件因為某種原因全部被分配到同一個位置，就產生類似 Hash Collision 的情況：

```text
01 號信箱
├── A 的信
├── B 的信
├── C 的信
├── D 的信
├── ...
└── Z 的信
```
此時即使已經找到正確 bucket，仍然必須進一步處理其中的多筆資料。

## 7. 為什麼同一系統需要同時使用 HashMap 與 PriorityQueue？

因為「依照 key 快速找資料」和「找出目前最高優先級資料」是兩種不同的操作需求。

HashMap 擅長的是： key &index，請幫我找到對應資料。

PriorityQueue 擅長的是：
請直接告訴我目前優先級最高的是誰。


以醫院急診系統為例。

當家屬到櫃檯詢問： 身分證字號 A123456789 的病人在哪裡？

系統可以進行檢查key ，平均可達 O(1)。

但醫師面對的問題可能完全不同：

> 現在等待的所有病人中，下一位最需要優先處理的是誰？

這時候重點不是病人的 ID，而是檢傷等級或其他 priority。

可以使用 PriorityQueue：

```text
PriorityQueue
     ↓
最高優先級病人
     ↓
次高優先級病人
     ↓
...

因此，同一組病人資料可以依照不同的存取需求，由不同資料結構提供不同的查詢方式
